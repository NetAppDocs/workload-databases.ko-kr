= Workload Factory의 데이터베이스 환경에 대한 구성 분석
:allow-uri-read: 
:icons: font
:imagesdir: ./media/


[role="lead"]
Workload Factory for Databases는 정기적으로 데이터베이스 구성을 분석하여 Amazon FSx for NetApp ONTAP 스토리지에 배포된 Microsoft SQL Server 및 Oracle에 문제가 있는지 확인합니다. 문제가 발견되면 Workload Factory는 문제의 원인과 해결 방법을 제시하여 데이터베이스 구성이 최상의 성능, 비용 효율성 및 모범 사례 준수를 달성하도록 도와줍니다.

Workload Factory는 잘 설계된 데이터베이스 워크로드를 위한 모범 사례 및 권장 사항을 제공합니다. 아키텍처 분석은 Microsoft SQL Server 및 Oracle Database의 스토리지, 컴퓨팅, 애플리케이션, 복원력 및 클론 생성과 관련된 구성 및 설정을 평가합니다.



[[how-it-works]]
== 작동 방식

Workload Factory는 Amazon FSx for NetApp ONTAP 파일 시스템 배포 환경에서 실행되는 워크로드를 매일 분석합니다. 이 분석을 통해 아키텍처 상태, 인사이트 및 권장 사항을 확인할 수 있습니다.

일일 분석이 완료되면 배포의 Well-architected 대시보드에 구성 상태가 "최적화됨" 또는 "최적화되지 않음"으로 표시됩니다. 총 최적화 점수, 범주별 구성 문제, 구성 문제 및 권장 사항 목록을 확인할 수 있습니다. 구성 문제에 대한 권장 사항을 검토할 수 있습니다. 일부 문제는 Workload Factory에서 자동으로 수정되지만, 다른 문제는 수동 개입이 필요합니다. 이 경우 Workload Factory는 권장 변경 사항을 구현하는 데 도움이 되는 자세한 지침을 제공합니다.

사용자 환경에 적용되지 않는 구성에 대한 분석은 제외할 수 있습니다. 이렇게 하면 불필요한 알림과 부정확한 최적화 결과를 방지할 수 있습니다.

또한 일반 언어로 사용자 지정 규칙을 만들어 조직 표준 및 NetApp 모범 사례에 따라 환경의 유효성을 검사할 수 있습니다. 모의 실행을 통해 규칙을 테스트한 다음, 모든 환경에서 실행되도록 예약할 수 있습니다. link:https://docs.netapp.com/us-en/console-well-architected/learn-custom-rules.html["사용자 지정 규칙에 대해 자세히 알아보기"^].



[[why-it-matters]]
== 중요한 이유

Workload Factory는 지속적인 평가와 권장 사항 인사이트 및 문제 해결을 결합하여 대규모 스토리지, 데이터베이스 및 VMware 환경에 모범 사례를 적용합니다. Workload Factory 콘솔에서 적용되는 자동화된 수정 사항은 인적 오류를 줄이고 일관된 관리를 보장하며 워크로드 인프라 전반의 성능과 안정성을 유지합니다.



[[options-for-analyzing-your-database-environment]]
== 데이터베이스 환경 분석 옵션

Workload Factory는 데이터베이스 환경을 분석하기 위한 다음 옵션을 제공합니다.

* *일회성 평가*: link:optimize-configurations.html["일회성 평가"]를 수행하여 자격 증명을 저장하거나 리소스를 등록하지 않고 Microsoft SQL Server 인스턴스 또는 Oracle 데이터베이스의 아키텍처가 잘 설계되었는지 확인할 수 있습니다.
+
일회성 평가의 경우, 분석하려는 Microsoft SQL Server 인스턴스 또는 Oracle 데이터베이스에 대한 자격 증명을 한 번만 제공하면 됩니다.

* *지속적인 평가*: Workload Factory는 데이터베이스 환경을 정기적으로 분석하고, 구성 최적화를 위한 지속적인 권장 사항을 제공하며, 문제를 자동으로 수정합니다.
+
지속적인 평가를 위해서는 AWS 계정에 리소스를 등록하고, 링크를 연결하고, 권한을 부여해야 합니다.





[[microsoft-sql-server-best-practices]]
== Microsoft SQL Server 모범 사례

다음 모범 사례 및 권장 사항은 Microsoft SQL Server 워크로드에 적용됩니다.



[[storage]]
=== 스토리지

.스토리지 계층
성능에 민감한 SQL 워크로드에는 기본 SSD 계층을 사용하십시오.

[%collapsible]
====
최적의 성능을 위해서는 FSx for ONTAP 볼륨에 기본 SSD 계층을 사용하십시오. 용량 풀 계층을 사용하면 성능이 저하되고 지연 시간이 증가할 수 있습니다. 기본 SSD 계층은 고성능 워크로드에 맞게 설계되었으며, 용량 풀 계층은 비용 효율성에 최적화되어 있어 SQL Server 워크로드의 성능 요구 사항을 충족하지 못할 수 있습니다.

====
.파일 시스템 여유 공간
전체 볼륨 크기보다 충분한 여유 용량을 확보하십시오.

[%collapsible]
====
파일 시스템 용량은 전체 볼륨 크기보다 충분히 확보하십시오. 여유 공간이 너무 적으면 성능 문제가 발생하고, 너무 많으면 저장 공간이 낭비되고 비용이 증가합니다.

====
.로그 드라이브 크기
로그 드라이브의 크기를 적절하게 조정하고 모니터링하여 롤백 및 서비스 중단을 방지하십시오.

[%collapsible]
====
SQL Server 로그 드라이브의 크기를 적절하게 관리하고 모니터링하여 로그 드라이브 용량 부족으로 인한 트랜잭션 롤백, 데이터베이스 사용 불가, 데이터 손상 및 성능 문제를 방지하십시오.

====
.TempDB 드라이브 크기
병목 현상과 시간 초과를 방지하도록 TempDB의 크기를 조정합니다.

[%collapsible]
====
성능과 안정성을 유지하려면 TempDB의 크기를 조정하고 모니터링하십시오. TempDB 공간이 부족하면 쿼리 속도 저하, 애플리케이션 시간 초과 및 시스템 충돌이 발생할 수 있습니다.

====
.데이터 및 로그 파일 배치
분리된  `.mdf` 및  `.ldf` 경로.

[%collapsible]
====
데이터 파일과 로그 파일을 서로 다른 드라이브에 분리하여 병렬 I/O, 백업 유연성 및 복원 동작을 개선하십시오. 소규모 데이터베이스의 경우 데이터 및 로그 LUN 경로를 서로 다른 볼륨으로 분리하는 것이 좋습니다.

====
.TempDB 배치
전용 드라이브를 사용합니다.

[%collapsible]
====
I/O 경합을 방지하고 SQL Server 성능 및 안정성을 향상시키려면 TempDB를 전용 드라이브에 배치하십시오.

====
.씬 프로비저닝
필요에 따라 스토리지를 할당합니다.

[%collapsible]
====
FSx for ONTAP 볼륨에 씬 프로비저닝을 구성하여 스토리지 활용도를 높이고 비용을 절감하십시오. 씬 프로비저닝을 사용하면 전체 용량을 한 번에 예약하는 대신 필요에 따라 스토리지를 할당할 수 있습니다.

====
.자동 크기 조정 및 자동 크기 조정 모드
볼륨을 자동으로 늘립니다.

[%collapsible]
====
자동 크기 조정 기능을 켜고 모드를 `grow` 설정하여 볼륨이 가득 차서 읽기 전용이 되기 전에 자동으로 증가하도록 합니다.

====
.블록 장치 공간 관리
SQL Server에서 사용하는 LUN에 대한 블록 장치 공간 설정을 구성합니다.

[%collapsible]
====
Microsoft SQL Server 인스턴스에서 사용하는 LUN의 블록 디바이스 공간 설정을 구성하여 쓰기 오류를 방지하고 FSx for ONTAP의 공간 효율성을 향상시킵니다.

====
.스냅샷 복사본 예약 및 자동 삭제
활성 데이터를 위한 공간을 확보하십시오.

[%collapsible]
====
활성 데이터에 필요한 공간을 확보하려면 스냅샷 복사본 예약률을 0%로 설정하고 스냅샷 자동 삭제를 활성화하십시오.

====
.공간 관리
스냅샷 복사본을 삭제하기 전에 볼륨을 확장하십시오.

[%collapsible]
====
저장 공간이 부족해지면 스냅샷 복사본을 삭제하기 전에 볼륨을 확장하십시오. 볼륨을 확장하면 "볼륨 용량 부족" 오류를 방지하고 쓰기 실패를 줄이며 스냅샷 복구 지점을 보존할 수 있습니다.

====
.계층화/TCO 최적화
스냅샷 전용 계층화 정책을 사용하여 스냅샷 데이터를 계층화합니다.

[%collapsible]
====
스냅샷 전용 티어링 정책을 사용하십시오. 이 정책은 활성 데이터를 SSD 티어에 유지하고 스냅샷 데이터만 용량 티어로 이동합니다. 이 접근 방식을 통해 SQL 워크로드의 저지연 성능을 유지하면서 스토리지 비용을 절감할 수 있습니다. 스냅샷 데이터는 7일의 쿨링 기간 후에 티어링됩니다.

====
.스토리지 효율성
중복 제거, 압축 및 컴팩션 기능을 사용하십시오.

[%collapsible]
====
성능을 유지하면서 스토리지 사용량과 비용을 줄이기 위해 중복 제거, 압축 및 컴팩션 기능을 활성화하십시오.

====
.OS 유형
ONTAP LUN OS 유형을 호스트 파티셔닝에 맞추십시오.

[%collapsible]
====
올바른 I/O 정렬을 유지하려면 ONTAP LUN 운영 체제 값을 호스트 파티셔닝 체계와 일치시키십시오.

====
.MPIO 정책, 세션, 상태 및 시간 초과 설정
멀티패스 I/O(MPIO) 정책, 세션, 상태 및 시간 초과 설정을 구성합니다.

[%collapsible]
====
복원력과 처리량을 위해 멀티패스 I/O(MPIO)를 구성하십시오. iSCSI LUN의 SQL Server에 대해 대상 인터페이스당 5개의 MPIO 세션을 사용하고, 경로 상태를 모니터링하며, 호스트 시간 초과를 60초로 설정하십시오.

====
.NTFS 할당 단위 크기
64K로 설정합니다.

[%collapsible]
====
SQL Server 워크로드의 디스크 효율성을 향상시키고 조각화를 줄이려면 NTFS 할당 단위 크기를 64K로 설정하십시오.

====
.예약된 로컬 스냅샷
예약된 스냅샷을 비활성화합니다.

[%collapsible]
====
Microsoft SQL Server에서 사용하는 FSx for ONTAP 볼륨에 대한 예약된 스냅샷을 비활성화하십시오. 대신 NetApp SnapCenter 등의 툴을 사용하여 외부에서 스냅샷을 관리하십시오. 이러한 툴은 애플리케이션 정합성 보장 백업을 생성하고 복원 작업 중 데이터 손상을 방지하는 데 도움이 됩니다.

====


[[compute]]
=== 컴퓨팅

.컴퓨팅 적정화
워크로드 수요에 맞춰 EC2 인스턴스 크기를 조정합니다.

[%collapsible]
====
워크로드 수요에 따라 SQL Server EC2 인스턴스의 크기를 적절하게 조정하십시오. 인스턴스 크기가 부족할 경우 늘리고, 과도하게 많을 경우 줄여 비용과 성능의 균형을 유지하십시오.

====
.운영 체제 패치
최신 OS 패치를 적용하십시오.

[%collapsible]
====
보안 및 안정성을 향상시키려면 최신 운영 체제 패치를 적용하십시오.

====
.네트워크 어댑터 설정
수신측 스케일링(RSS)을 구성합니다.

[%collapsible]
====
수신측 스케일링(RSS)을 구성하여 네트워크 처리를 CPU에 분산시켜 네트워크 성능을 향상시키십시오. 실제 운영 환경에 배포하기 전에 설정을 검증하십시오.

====
.MTU 정렬
호스트 및 스토리지 경로 전체에 걸쳐 최대 전송 단위(MTU)를 정렬합니다.

[%collapsible]
====
단편화를 방지하고 안정적인 처리량을 유지하려면 FSx for ONTAP 경로에 대해 EC2 최대 전송 단위(MTU) 설정을 일치시키십시오.

====


[[application]]
=== 애플리케이션

.라이센스
유료 기능에 대한 라이선스 사용량을 검토합니다.

[%collapsible]
====
호스트 수준에서 SQL Server 라이선스 사용 현황을 검토하십시오. 유료 기능을 사용하지 않는 경우 라이선스가 최적화되지 않아 비용이 증가할 수 있습니다.

====
.Microsoft SQL Server 패치
최신 SQL Server 패치를 적용하십시오.

[%collapsible]
====
보안 및 시스템 안정성을 향상시키려면 최신 SQL Server 패치를 적용하십시오.

====
.MAXDOP
워크로드 테스트를 거친 값을 사용하십시오.

[%collapsible]
====
쿼리 성능을 최적화하려면 MAXDOP를 구성하십시오. 일반적으로 4, 8 또는 16 값이 적합합니다. 워크로드를 테스트하고 CXPACKET과 같은 병렬 처리 대기 유형을 모니터링하십시오.

====


[[resiliency]]
=== 복원력

.애플리케이션 정합성 보장 스냅샷
애플리케이션 정합성 보장 스냅샷을 NetApp SnapCenter와 함께 사용합니다.

[%collapsible]
====
애플리케이션 정합성 보장 스냅샷을 NetApp SnapCenter와 함께 사용하여 특정 시점의 볼륨 데이터 스냅샷을 정확하고 안정적으로 생성할 수 있습니다. SnapCenter는 백업을 간소화하고 데이터 복원 속도를 높여 다운타임을 줄이고 중요 워크로드를 보호합니다.

====
.지역 간 복제
지역 장애로부터 보호합니다.

[%collapsible]
====
SQL Server 환경에서 데이터 가용성과 재해 복구를 향상시키려면 지역 간 복제(CRR)를 활성화하십시오. CRR은 여러 위치에 데이터를 복제하여 지역 장애로부터 보호하고 비즈니스 연속성을 보장합니다.

====
.백업 구성
FSx for ONTAP 백업 또는 AWS Backup을 구성합니다.

[%collapsible]
====

[%collapsible]

[%collapsible]

Oracle ASM Filter Driver(AFD)와 ASMLib이 기본 FSx for ONTAP 스토리지의 논리 블록 크기를 사용하도록 구성합니다.

+
[%collapsible]
====
ASMLib 구성 파일에서 Oracle ASM 필터 드라이버(AFD) 및 ASMLib를 구성하여 기본 FSx for ONTAP 스토리지의 논리 블록 크기를 사용하도록 설정하십시오. 이렇게 하면 AFD 및 ASMLib가 스토리지의 블록 크기에 맞춰 I/O 작업을 수행하여 지연 시간을 최소화하고 불필요한 I/O 오버헤드를 줄여 성능을 최적화할 수 있습니다.

.TCP 슬롯 테이블
NFS 기반 Oracle 워크로드의 경우 128로 설정합니다.

[%collapsible]
====
NFS에서 실행되는 Oracle 워크로드의 경우 TCP 슬롯 테이블의 커널 매개변수를 128로 구성하십시오. 이 구성을 통해 더 많은 동시 I/O 작업을 처리할 수 있으므로 Oracle 데이터 파일 액세스 등 고처리량 시나리오에서 지연 시간이 줄어듭니다. 커널 매개변수는 TCP를 통한 최대 NFS 요청 대기 수를 제어하며, 파이버 채널 설정의 큐 깊이와 유사하게 작동합니다. 일반적으로 16으로 설정되는 Linux의 기본값은 최적의 데이터베이스 성능을 지원하지 않습니다.

====
.NFS 마운트 옵션 - 데이터베이스 파일
데이터베이스 파일의 성능을 최적화하는 NFS 마운트 옵션을 사용하십시오.

[%collapsible]
====
데이터베이스 파일에 최적화된 NFS 마운트 옵션을 사용하십시오. 주요 매개변수에는  `rw`읽기/쓰기 액세스,  `bg`백그라운드 마운트,  `hard`실패 시 무한 재시도 및  `proto=tcp`안정적인 전달이 포함됩니다.  `rsize` 및  `wsize` 값 262144는 대규모 I/O 작업을 개선하여 처리량을 향상시키는 동시에  `nointr`은(는) 장시간 실행되는 작업을 중단하지 않습니다. 이 구성은 특히 처리량이 높은 환경에서 데이터베이스 성능과 복원력을 향상시킵니다.

====
.ADR 홈용 NFS 마운트 옵션
ADR 홈 디렉토리의 성능을 최적화하는 NFS 마운트 옵션을 사용합니다.

[%collapsible]
====
자동 진단 저장소(ADR) 홈 또는 루트 디렉터리에 최적화된 NFS 마운트 옵션을 사용하십시오. ADR 홈에는 로그 및 추적 정보가 저장되는데, 이러한 정보는 핵심 데이터베이스 파일과 유사한 안정성 옵션의 이점을 누리지만, 작업이 중단에 덜 민감하므로 `nointr` 마운트 옵션이 필요하지 않습니다.

.NFS 캐싱 옵션
독립 실행형 배포 환경에서는 호스트 캐싱을 비활성화하지 마십시오.

[%collapsible]

dNFS를 활성화합니다.

[%collapsible]

Oracle 환경에서 Direct NFS(dNFS)를 활성화하여 NFS 스토리지 성능과 안정성을 향상시키십시오.

라운드 로빈 방식의 이름 확인을 피하십시오.

[%collapsible]
====
DNS, DDNS, NIS 또는 기타 모든 라운드 로빈 이름 확인 방식을 사용하는 경우 Direct NFS(dNFS) 사용을 피하십시오. 여기에는 ONTAP에서 사용 가능한 DNS 로드 밸런싱 기능이 포함됩니다. 일관된 IP 주소 확인은 데이터베이스 안정성을 유지하고 잠재적인 충돌이나 데이터 손상을 방지합니다.

====
.dNFS 구성 파일
Validate `oranfstab` 콘텐츠 유효성을 검사합니다.

[%collapsible]
====
 `oranfstab` 파일 내용을 확인하고 업데이트하여 Direct NFS(dNFS)를 올바르게 사용하십시오. 이  `oranfstab` 파일은 멀티패싱 및 특정 NFS 옵션 등 고급 dNFS 기능을 구성하는 데 필수적입니다. 올바른 구성은 데이터 액세스 및 관리 효율성을 향상시킵니다.

====
.dNFS 공유 캐시 없음
특정 멀티 마운트 케이스에  `nosharecache`을 사용하십시오.

[%collapsible]
====
Direct NFS(dNFS)가 활성화되어 있고, 소스 볼륨이 중첩된 NFS 마운트를 통해 단일 서버에 두 번 이상 마운트된 환경에서 `nosharecache` 마운트 옵션을 구성하십시오. 이 구성은 마운트 간 캐시 공유를 방지하여 데이터 일관성과 최적의 성능을 보장합니다.

====


[[compute]]
=== 컴퓨팅

.운영 체제 패치
최신 패치를 적용합니다.

[%collapsible]
====
보안 및 안정성을 향상시키려면 최신 운영 체제 패치를 적용하십시오.

====
.Transparent huge pages
투명 대용량 페이지(THP)를 비활성화합니다.

[%collapsible]
====
잠재적인 성능 저하를 방지하고 메모리 관리를 개선하려면 Oracle 데이터베이스를 실행하는 데이터베이스 호스트에서 THP(Transparent Huge Pages)를 비활성화하십시오.

====
.TCP 고급 옵션
TCP(전송 제어 프로토콜) 고급 옵션을 활성화하십시오.

[%collapsible]
====
최상의 네트워크 성능과 안정성을 위해 TCP 타임스탬프, SACK 및 윈도우 스케일링을 활성화하십시오.

====
.파일 시스템 I/O 옵션
설정 `filesystemio_options = setall`.

[%collapsible]
====
최적의 I/O 성능을 위해  `filesystemio_options = setall`을 설정하십시오. 버퍼링된 I/O에서 벗어나는 경우 필요에 따라 시스템 전역 영역(SGA) 크기를 조정하십시오.

====
.멀티블록 읽기 횟수
 `db_file_multiblock_read_count` 매개변수를 제거합니다.

[%collapsible]
====
Oracle 데이터베이스의 성능 문제를 방지하고 Oracle이 이 설정을 자동으로 관리할 수 있도록 텍스트 기반 FILE `init.ora` 또는 서버 관리형 바이너리 SPFILE (`spfile<SID>.ora`)에서  `db_file_multiblock_read_count` 매개변수를 제거합니다.

====
.Oracle Critical Patch Updates
최신 CPU 업데이트를 적용합니다.

[%collapsible]
====
최신 Oracle 중요 패치 업데이트를 적용하여 보안 취약점을 해결하고 데이터베이스 환경의 무결성을 유지하십시오. 잠재적인 위협으로부터 보호하고 보안 모범 사례를 준수하려면 정기적으로 패치를 검토하고 적용하십시오.

====


[[resiliency]]
=== 복원력

.애플리케이션 정합성 보장 스냅샷
애플리케이션 정합성 보장 스냅샷을 NetApp SnapCenter와 함께 사용합니다.

[%collapsible]
====
애플리케이션 정합성 보장 스냅샷을 NetApp SnapCenter와 함께 사용하여 특정 시점의 볼륨 데이터 스냅샷을 정확하고 안정적으로 생성할 수 있습니다. SnapCenter는 백업을 간소화하고 데이터 복원 속도를 높여 다운타임을 줄이고 중요 워크로드를 보호합니다.

====
.지역 간 복제
지역 장애로부터 보호합니다.

[%collapsible]
====
Oracle 데이터베이스의 데이터 가용성과 재해 복구 기능을 향상시키려면 지역 간 복제(CRR)를 활성화하십시오. CRR은 여러 위치에 데이터를 복제하여 지역 장애로부터 보호하고 비즈니스 연속성을 보장합니다.

====
.백업 구성
FSx for ONTAP 백업 또는 AWS Backup을 구성합니다.

[%collapsible]
====
FSx for ONTAP 백업 또는 AWS Backup을 구성하여 데이터 보존 및 규정 준수 요구 사항을 충족하고 중복 백업 워크플로를 방지하십시오.

====

=== 클로닝

.클론 정리
오래된 클론은 정기적으로 삭제하십시오.

[%collapsible]
====
저장 비용과 운영상의 혼란을 줄이려면 더 이상 사용하지 않는 클론을 정기적으로 제거하십시오. 오래되고 사용하지 않는 클론은 높은 비용을 초래합니다.
